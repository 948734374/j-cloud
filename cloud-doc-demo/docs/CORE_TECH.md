# 核心技术与难点技术

## 核心技术

### 1. WebSocket 实时通信

多人协同编辑需要服务端主动推送内容变化。项目通过 WebSocket 建立浏览器与服务端的长连接，编辑变更可以实时广播给同一文档中的其他用户。

### 2. 文档房间模型

每篇文档对应一个房间：

```text
doc-product-plan
  - Alice
  - Bob
  - Charlie
```

用户打开文档时加入房间，关闭页面或连接断开时离开房间。服务端只向当前房间广播消息。

### 3. 自动保存

前端编辑时不会每个按键都立即发送，而是经过短防抖后发送当前文档内容。服务端收到后立即写入本地 JSON 文件，并返回保存成功状态。

### 4. 在线用户展示

服务端维护每个房间内的连接集合。用户加入或离开时，服务端广播 `presence:update`，前端刷新在线头像列表。

### 5. 远端光标同步

前端监听本地编辑器选区变化，发送当前光标的 DOM 路径、节点偏移、换行感知的文本偏移，以及相对编辑器的坐标兜底值。其他客户端收到后优先用 DOM 路径定位到编辑器内部，路径失效时再用文本偏移或坐标兜底渲染，因此空行和换行位置也能显示彩色光标。标签文本最多显示 3 个字符。多个用户位于同一编辑位置时，前端按光标坐标分组，将用户名标签纵向堆叠，并用小三角形连接到光标线。

### 6. 本地持久化

Demo 使用 `data/documents.json` 保存文档数据。写入时先写临时文件，再重命名覆盖正式文件，减少写入中断导致的数据损坏风险。

## 难点技术

### 1. 编辑冲突

第一阶段采用整篇内容同步，多个用户同时编辑同一位置时可能发生后写覆盖先写。该策略适合 Demo，但不适合生产环境。

生产环境应使用 CRDT 或 OT：

- CRDT：Yjs、Automerge
- OT：Operational Transformation

推荐第二阶段接入 Yjs，将服务端从“理解文档内容”改为“转发和持久化 CRDT update”。

### 2. 断线重连

当前 Demo 断线后重新打开文档会加载服务端最新快照。生产环境需要在客户端保留 state vector，并在重连后只同步缺失的增量。

### 3. 多节点部署

当前 Demo 是单进程内存房间模型。如果部署多个 WebSocket 节点，同一文档的用户可能连接到不同节点，需要 Redis Pub/Sub 或消息队列同步节点间消息。

### 4. 高频编辑性能

协同编辑消息频率很高。第一阶段通过前端防抖降低写入次数。生产环境应继续加入：

- 增量同步
- 批量落盘
- 快照压缩
- 服务端限流
- 大文档分块

### 5. 富文本结构一致性

`contenteditable` 在不同浏览器中生成的 HTML 可能略有差异。生产环境建议使用 ProseMirror / Tiptap 这类结构化编辑器，统一文档 schema 和编辑命令。
